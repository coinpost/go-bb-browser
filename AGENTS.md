# AGENTS.md

Agent-facing notes for this repository.

## Intent

Mirror the **bb-browser** shape — **CLI → HTTP daemon → Chrome via CDP only** — while implementing in **Go** and using **chromedp** as the CDP client library.

**Scope:** **Google Chrome only**; **no Chrome extension** and **no multi-browser support** — all automation goes through CDP from the daemon. The **daemon never starts the browser**; it only **attaches** to an already-running Chrome with a DevTools debugging endpoint (e.g. `--remote-debugging-port`).

Upstream reference architecture (TypeScript): CLI and MCP talk HTTP to a daemon; the daemon holds CDP connections, dispatches commands, and maintains per-tab state with ring buffers and a global monotonic `seq`.

## Design invariants (ported from bb-browser)

Preserve these invariants:

1. **INV-1:** Operational responses include the **tab id** (the complete CDP target id) and **`seq`**.
2. **INV-2:** Observation-style responses (network / console / errors) include a **cursor** for incremental reads.
3. **INV-3:** Invalid tab id → **hard error** (no silent fallback). A tab id is the **complete CDP target id, verbatim**: exact byte match only — no short alias, prefix/suffix, case-folding or trimming, and never the focused or any other tab in place of an id that was supplied.
4. **INV-4:** **`seq` is globally monotonic** (never decreases).
5. **INV-5:** Events are **isolated per tab** in queries.
6. **INV-6:** Tab close → the id stops resolving (it never comes to mean another target) and that tab’s buffers are **cleared**.
7. **INV-7:** `tab_new` must work when **zero** tabs exist (ordering vs `ensurePageTarget` matters).

## When code exists

- **Build:** `go build -o bb-daemon ./cmd/bb-daemon`
- **Test:** `go test ./...`
- **Real-Chrome acceptance (opt-in, build tag `realchrome`, never part of `go test ./...`):** `BB_REAL_CHROME=<Google Chrome binary> BB_REAL_CHROME_EVIDENCE=<dir> go test -tags realchrome -race -count=5 ./internal/daemon -run '^TestRealChrome'`. Each test starts its own **non-headless** Chrome (throwaway profile, DevTools on `127.0.0.1` with a port Chrome picks, DNS disabled) and the production daemon (`NewServer` + `ListenAndServe`) behind a loopback proxy that logs every CDP frame (`cdp.jsonl`) and can only delay real replies / notifications — it never fabricates a frame and never enables discovery. It never touches another Chrome. Chrome 157 refuses `Target.createTarget` with no window open, so the zero-page cases skip as *not verified*.
- **Daemon:** `bb-daemon` requires `--debugger-url` (or `BB_BROWSER_DEBUGGER_URL`) — e.g. host:port after starting Chrome with remote debugging (`127.0.0.1:9222`). On startup it **attaches via chromedp** (`NewRemoteAllocator` only). Optional **`--tab-idle-timeout`** / **`BB_BROWSER_TAB_IDLE_TIMEOUT`** (default `5m`, `0` disables) closes **daemon-created** tabs after idle; tab-related RPC lines (`action` + JSON-RPC request `body`) append to **`rpc.jsonl`** under **`--state-dir`** / **`BB_BROWSER_STATE_DIR`** (default `~/.local/state/bb-daemon`; `--state-dir -` uses in-memory mode: RPC lines are validated and update managed-tab activity but no history is retained). The global **`seq`** is seeded from the wall-clock nanosecond at startup and incremented in memory (no persisted counter). Persisted managed-tab membership is keyed by **full CDP target id** and changed only by lifecycle records the store writes synchronously (`store.RegisterManagedTab` → `managed_tab_open` when `tab_new` commits its created target; `store.RetireManagedTarget` → `managed_tab_retire` on successful `tab_close`, a close answered with target-gone, idle close, target-destroyed event, or absence from a **successful** target enumeration). Both are written inside the lifecycle critical section (`Server.lifeMu`, see below), registry first, so no open record can follow the removal of its target. RPC audit lines (asynchronous; `target` is the complete CDP target id the request was resolved to, absent for unresolved requests) never add or remove membership — they only refresh last-activity of the managed target with exactly that id — so a delayed line cannot resurrect a retired tab or touch another tab. Failed closes (other than target-gone) and failed enumerations must not retire. Managed invariant: the idle tracker holds only registered targets and the persisted set holds at least those; the two differ only by members a **previous daemon process** persisted that this one has not settled yet. Those are settled by the first successful enumeration, whichever request it belongs to (`recoverManagedLocked`, inside `applyEnumeration`): registered → idle tracking resumes; not listed by the reply itself → retired; listed but not accepted by the registry → kept and the enumeration is requested again (`MarkTargetDirty`; defensive — whatever made the registry refuse it retired it in the same critical section). A tab created by `tab_new` enters both sets in one step and is never judged by a reply that overlaps its creation. Idle recovery replays `rpc.jsonl` and restores a tab only when a live target has exactly the persisted full target id. Records without `target` — unresolved requests, and everything written by daemons that logged a short alias under `tab` (a key no longer written or read) — identify no tab and are skipped (one startup warn for such `tab_new` records); never adopt a tab from a short alias or from the `tab` in a request body. A lifecycle write error still updates memory and is logged as warn, never treated as durable. `rpc.jsonl` auto-rotates past **`--rpc-log-max-bytes`** / **`BB_BROWSER_RPC_LOG_MAX_BYTES`** (default 8 MiB) into numbered backups (`rpc.jsonl.1`…, 3 kept); the fresh log is seeded with a snapshot of currently managed tabs (one `managed_tab_open` each, with full target id + last-activity time; retired tabs are not reseeded) so recovery only needs the current file. Replay splits on physical newlines: a corrupt newline-terminated line is warned and skipped (kept on disk, later records still replayed, glued records are not guessed apart); a complete final record missing its newline is replayed and the next write first restores the line boundary; an incomplete final record is truncated. After a failed/short write the next write (append or rotation snapshot) also emits the separator first and refuses to append while that fails. The log keeps request bodies (possibly secrets), so the state dir is created **`0700`** and `rpc.jsonl` plus backups **`0600`** regardless of umask; on startup an existing state dir, active log and `.1`–`.3` backups with wider modes are tightened before replay (stricter modes are never loosened, other files and parent dirs are untouched, a failed chmod fails startup; no-op on Windows). **`POST /v1`** accepts **JSON-RPC 2.0** bodies: **`method`** replaces the old **`action`** field (same string values); arguments live in **`params`**. Methods include **`tab_new`** (optional `url`, optional **`silent`** to open in background without changing focus), **`goto`** (`tab` + `url`), **`tab_close`**, **`tab_select`**, **`tab_list`**, plus **`screenshot`**, **`eval`**, **`click`**, **`fill`**, observation **`network`**, **`console`**, **`errors`** (`tab` + optional **`since`**; **`result`** includes **`events`**, **`cursor`**, optional **`dropped`** — INV-2). Successful **`result`** objects include **`seq`**; **`tab`** when applicable (INV-1).

**Tab identity (breaking change):** short tab ids are gone. `tab` / `focus` / `tabs[].tab` in results and the `tab` param of every targeted method are the complete CDP target id as an opaque string; CLI `--tab` / `--id` pass it verbatim (an explicitly empty `--tab` is an error, not the focused tab). Only the empty string is "missing" (`missing tab` / CLI empty-id error); every other value, whitespace-only included, is looked up byte for byte — do not `TrimSpace` a tab id to test for emptiness. `TabRegistry` keeps no alias layer: `Lookup` is an exact match on registered page targets. A request resolves its tab once (`resolveTab` → `pinTarget`); the per-tab operation lock key, the CDP command, the idle renewal and the audit `target` all use that one id and nothing is re-resolved later — a request that waited for the lock of a tab that vanished meanwhile fails with `unknown tab id`. Only `tab_list` / `tab_focus` (and the CLI when `--tab` is omitted) use the focused tab. `tab_select` takes the same lock as every other targeted method, so it cannot succeed or renew the idle clock while an idle close of that tab is in progress.

**Lifecycle model (design: one clock, request windows, no history):** the browser is the authority; a reply or event is evidence about one moment. "Gone" is permanent once observed (ids are not reused within a browser session); "exists" is only true for its moment. `TabRegistry` orders all evidence on **one clock** on which every window opening, every lifecycle event **read** from the connection and every application of evidence is a distinct instant; it keeps the known targets and the `Window`s of browser requests in flight, nothing else. Per known target it keeps **`seen`** — the earliest instant by which the target is proven to have existed (read stamp of the event, application of the enumeration, or commit of the creation that registered it) — and **never renews it**. `OpenWindow` before `Target.getTargets` / `Target.createTarget`; exactly one of `ApplyEnumeration` / `CommitCreated` / `Abandon` ends it (every error/cancel path abandons). While open, a window records what was reported gone (`removed`, every report counts, known or not) and the intersection of the page sets of enumerations applied meanwhile (`listed`). **Absence has three outcomes only.** An enumeration `W` that does not list a known target: `seen < W.opened` → gone (the snapshot is provably newer): removed, reported, recorded in the windows in flight — this is the only enumeration outcome that unregisters; otherwise the two cannot be ordered and `ApplyEnumeration` returns `verify` (a fresh enumeration **must** be requested — `requestEnumeration` → `MarkTargetDirty`; it is opened after every `seen` involved, so it settles the question), and meanwhile a **first-hand** target (committed by `CommitCreated`, or registered by a lifecycle event) stays resolvable — this protects a concurrent `tab_new` from an earlier, even empty, snapshot — while a **discovery** (only enumerations ever listed it) is **suspended**: `Has`/`Lookup`/`Select` fail, but it stays `Known` and keeps `seen`, observation buffers, idle tracking, managed record and its chromedp attachment. The rule is symmetric: a reply that lists an unknown target which an enumeration applied while its window was open did not list registers it suspended and also returns `verify`. A suspended target is resumed or removed by the next enumeration that can be ordered (the automatic one, or `resolveTab`'s). Do not turn suspension into removal, and do not give discoveries the creation protection back: the first released the browser attachment of a live page (chromedp then sends `Target.closeTarget` — a read-only conflict closed a user tab), the second kept a destroyed tab resolvable. **`Session.ForgetTarget` (which cancels the chromedp child context and thereby closes the page if it is still open) may only follow a removal the registry reported**: close reply, destroyed notification, or the "gone" outcome above; `Target.closeTarget` itself is only sent by the explicit close paths (`tab_close`, idle close, `tab_new` rollback). An enumeration registers an unknown listed target unless it is in the window's `removed`. `CommitCreated` refuses a target in its window's `removed` **whether or not it is known again right now** (and a doomed one), leaves an already known target's `seen` unchanged (so a later enumeration that no longer lists it still removes it), makes it first-hand, and returns `verify` when unordered absence evidence exists (the target was suspended, or an enumeration applied while the window was open did not list it); `commitCreatedTab` then asks the browser once more **before `tab_new` answers** (that enumeration is requested after the commit, so not listing the tab proves it gone and removes it with its managed record → `tab closed before tab_new completed`); only if that enumeration fails is the question left to the sync loop. Memory is bounded by requests in flight plus the targets the browser listed; with no request in flight no removal or snapshot evidence exists. Do not reintroduce removal/snapshot history rings or "unverifiable" fallbacks. **Lifecycle events:** the production connection enables them itself — `browser.Connect` sends a **root-level `Target.setDiscoverTargets{discover:true}`** (browser executor, no `sessionId`) after registering its listener; chromedp only enables discovery on the page session it attaches, whose notifications never reach `ListenBrowser`, so without the root command the daemon is told nothing and a tab closed in the browser lingers until some RPC enumerates. A refusal is not fatal (`Session.TargetDiscoveryErr`, one startup warn; removal is then learned from enumerations only). Tests must not hand the daemon lifecycle events its production connection would not get: the CDP stub only sends them after that root-level command. The registry is the connection's `browser.TargetObserver` (`browser.WithTargetObserver(s.tabs)`, installed by `connectBrowserLocked` before the first request). The reader's order in `Session.enqueueTargetEvent` is a contract: **`NoteEventRead`** (returns the event's stamp; for a destroyed notification the target is **doomed** — it stops resolving at once — and its id is written into `removed` of every window in flight, so neither a late `Target.createTarget` reply nor an enumeration that still lists it can register it) → queue → if the queue is full **`EventDropped`** (queued older "exists" events can no longer register an unknown target) → **only then** is the overflow published (`targetDirty`). Whoever consumes the dirty flag therefore requests its enumeration after everything the dropped event meant was recorded; do not publish first. Observer methods run on the connection reader: they only touch the registry mutex and never unregister (that needs `lifeMu`); a doomed target is cleaned up by the queue consumer (`RemoveEventTarget`) or by **any** enumeration applied next, whatever it lists. `RegisterEvent(stamp, id)` registers an unknown page target first-hand with `seen = stamp` — the instant the event was **read**, not handled, so an enumeration requested after that and not listing it still removes it — and refuses (caller requests an enumeration) when an enumeration, a command-reply removal (`RemoveTarget`) or a queue overflow was applied after the stamp; destroyed / non-page events are always applied as removals (ordered by the queue). Evidence time, not handling time, decides what may re-register a target Chrome still lists after a confirmed close (until its destroyed event): an enumeration **requested after** the close was applied, or a page info event (created / info changed) **read after** it; replies requested and events read before it cannot. **`Server.lifeMu`** serializes the *application* of evidence (never held across a browser round trip): registry first, then observation buffers, idle tracking and persisted managed records (`applyEnumeration`, `commitCreatedTab`, `removeTargetState` / `removeEventTarget`); lock order `lifeMu` → registry / idle / store. `tab_close` applies both a successful close and an explicit target-gone answer (error still returned). A `tab_new` whose commit is refused (or whose tab the verification right after the commit found gone) returns `tab closed before tab_new completed`, registers/manages/selects nothing, and rolls the created id back with one bounded close (`createRollbackTimeout`, outcome in `data.hint`); a creation request that fails or times out yields no id and cannot be rolled back. Do not reintroduce alias generation/parsing, normalization, or fallback; CDP target ids are not promised unique across browser restarts and there is no ownership/lease protocol. Errors use JSON-RPC **`error`** (`code`, `message`, optional **`data`**).

Layout: `cmd/bb-daemon` (daemon); `internal/daemon` (HTTP server, JSON-RPC dispatch); `internal/browser` (remote CDP session); `internal/store` (RPC log + seq); `pkg/protocol` (JSON-RPC + params/result types, importable by dependents); `pkg/daemonclient` (`NewClient` one daemon; `NewPool` many daemons with even spread, per-daemon headers, tab affinity; Pool tab ids are `<backendKey>:<targetId>`); `internal/state` (tab registry, observation buffers).

**Operation budget:** `internal/timeout.Operation` (60s) is the single source for both the daemon's per-RPC CDP deadline and the CLI's whole-command budget (`run` included: tab selection + `eval` share it). Timeout errors name the limit; docs quoting it are checked by `internal/timeout` tests. Do not give the CLI or docs a larger number without raising the daemon limit and `http.Server.WriteTimeout`.

**Optional API token:** daemon merges repeated `--api-token`, comma-separated `BB_BROWSER_API_TOKEN`, and `--api-token-file` / `BB_BROWSER_API_TOKEN_FILE` (flag overrides file environment path; one token per line, blank and `#` comment lines ignored). Trim, deduplicate, ignore empty entries; an empty whitelist disables auth. Unreadable files fail startup without exposing secrets. Configured `POST /v1` (except the explicitly enabled loopback exemption below) requires `Authorization: Bearer <token>`; compare every whitelist entry with `crypto/subtle.ConstantTimeCompare`, without early match returns. Failures return standard HTTP 401 (`unauthorized\n`, plain text, `WWW-Authenticate: Bearer`) before reading the body, RPC dispatch or audit, so no `rpc.jsonl` write. `/live`, `/ready`, `/health` remain public. Never log API tokens. With no tokens, non-loopback listening only emits a startup warn. CLI `--api-token` / `BB_BROWSER_API_TOKEN` sends one token (flag overrides environment); `daemonclient.WithAPIToken` adds the header per client, including independent Pool backend tokens. Whitelist changes require restart; TLS, roles and health auth are out of scope.

**Optional loopback exemption:** `--api-token-allow-loopback` / `BB_BROWSER_API_TOKEN_ALLOW_LOOPBACK` defaults to false (standard `strconv.ParseBool` values; invalid/empty environment values fall back to false; flag overrides environment). With tokens configured, direct TCP loopback `POST /v1` requests without proxy headers bypass Authorization entirely, including wrong tokens. Only `r.RemoteAddr` establishes loopback (`127.0.0.0/8`, `::1`, IPv4-mapped IPv6, with a numeric 0-65535 port; malformed addresses fail closed); never trust `Host` or forwarded addresses. The package-level `proxyHeaders` list contains `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`, `Forwarded`, `CF-Connecting-IP`, `CF-Ray`, `True-Client-IP`, `Via`, `X-Forwarded-Server`, `X-Forwarded-Port`, `X-Forwarded-Scheme`, `X-Original-Forwarded-For`, `Forwarded-For`, `X-Client-IP`, `X-Cluster-Client-IP`; any of these or any `Tailscale-` prefix header disables exemption (case-insensitive presence, even empty values). Normal token authentication then applies. Startup logs one warn with tokens, or an info explaining no effect without tokens; no per-request exemption logs or secrets. Health routes and clients are unchanged. Direct local callers and Tailscale HTTP forwarding (Serve/Funnel default mode, proxy headers preserved) may enable it; forwarded calls still require tokens. Never enable for TCP forwarding (including `tailscale serve --tcp` / `--tls-terminated-tcp`), local reverse proxies that may strip headers, Docker port mappings, cloudflared, or uncertain proxy paths. Header detection is only a fallback, not the primary defense. [Official Serve docs](https://tailscale.com/docs/features/tailscale-serve#identity-headers) document identity headers and their absence for tagged devices/Funnel; [official proxy source](https://github.com/tailscale/tailscale/blob/main/ipn/ipnlocal/serve.go) additionally confirms forwarded headers and `Tailscale-Funnel-Request` (not confirmed in official docs, not live-tested).

**Multi-daemon:** do not put a daemon pool inside callers (e.g. feedscrawler). Use `daemonclient.NewPool(NewClient(urlA, WithHeader(...)), NewClient(urlB, WithHeader(...)))`. Tabs are not shared across daemons. Pool-facing tab ids are `<backendKey>:<targetId>` — the daemon’s complete CDP target id behind the backend key (backendKey defaults to the 0-based constructor index; `NewPoolBackends` can set a name) — matched exactly; a bare target id is rejected rather than guessed onto a backend. `TabNew`, `TabList`, and `TabFocus` return that form; later ops parse the prefix, strip it, and send only the daemon’s own tab id to that backend (no cross-daemon forward/failover). `TabList` queries every backend concurrently, prefixes each id, and merges in constructor order (a down backend is skipped; `*AllFailedError` only if all fail). `TabFocus` also asks all backends concurrently and returns the first healthy one in constructor order (not the fastest), prefixed — not a pool-wide focus. Both wait at most 2s (or the caller's shorter deadline): a backend that has not answered is skipped and its request cancelled, successes already received are returned; with none, the caller's context error (deadline passed) or `*AllFailedError`. Only a success fully decoded inside that budget counts; one completed at or after the deadline is treated as timed out even if it arrives before the call returns. Caller cancellation aborts with `context.Canceled`, discards every answer already received and binds nothing and leaves the caller's result untouched: prefixed results and the whole batch of binding additions and retirements are staged first (the result is decoded into a fresh value outside the lock), and the final cancellation check runs under the pool's tab lock immediately before that batch is committed, so a cancel during fan-out, result preparation or the lock wait still wins; only a cancel after that check is too late. A passed deadline is not a cancellation (in-budget successes are still committed). On success the staged value replaces `*result` as a whole. Each request runs from a snapshot of its backend `Client` (`HTTP`, `BaseURL`, cloned `Headers`, request id from that Client's counter) taken before any request starts, so reconfiguring a `Client` after the call returns is safe. Background requests never change bindings or write the caller's result.

A backend's successful `tab_list` is authoritative for that backend: its bindings no longer in `tabs` are retired (later ops return `*UnknownTabError` locally); failed backends are not reconciled (a reply whose `tabs` is missing, `null` or not an array counts as failed — only an explicit `[]` empties a backend). Only list entries supply binding evidence. A list's `tab` / `focus` fields are metadata. `TabFocus` supplies fresh evidence for the ids it reports and never retires tabs. Ordering uses a pool-local logical clock under a short lock (never across I/O), not daemon `seq`: each `tab_list` / `tab_focus` is evidence of the generation at which it was **sent**; a list retires only bindings whose evidence is older than it, observations older than the newest adopted list are ignored, so a late older list cannot retire newer `tab_new` / observed bindings nor override a newer list, and a newer observation re-binds a live tab an older list retired. `tab_close` / `ForgetTab` take effect when they happen (in-flight older observations cannot revive the id, later ones can); their marks are reclaimed against the earliest in-flight observation (see `pkg/daemonclient/README.md`). Malformed or unknown-prefix ids are rejected. Observed ids are bound exactly as returned (never trimmed). When the backend a tab is bound to answers the explicit `unknown tab id`, the Pool returns `*UnknownTabError` (pool id in `Tab`) wrapping that `*RPCError`; other RPC errors pass through and the binding is left to the reconciliation rules above. `NewPool` does not health-check at startup. Unbound `tab_new` may fail over to another daemon only to **open a new tab** there.

## Cursor Cloud specific instructions

- **Toolchain:** This module targets **Go 1.26** (`go.mod`). The distro's default `go` is older, so Go 1.26 is installed at `/usr/local/go` and symlinked as `/usr/local/bin/go` (system dep, baked into the VM snapshot). The startup update script only runs `go mod download`. Standard build/test commands are in the README / "When code exists" section above.
- **Running end-to-end requires a real Chrome — the daemon never launches it.** Chrome is preinstalled (`google-chrome`). There is no display, so launch **headless**: `./bb-browser launch --headless --port 9222` (prints `host:port`), then `./bb-daemon --debugger-url 127.0.0.1:9222 --listen 127.0.0.1:8787`. Verify with `./bb-browser health` or `curl 127.0.0.1:8787/health` (`{"status":"ok","browser":"connected"}`; HTTP 503 when CDP is down). The CLI defaults to `http://127.0.0.1:8787`.
- **Gotcha:** `screenshot` on a `data:` URL tab hangs in headless Chrome. Use a real navigable page (`http(s)://` or `file://`) when capturing screenshots.
