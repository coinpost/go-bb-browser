# AGENTS.md

Agent-facing notes for this repository.

## Intent

Mirror the **bb-browser** shape — **CLI → HTTP daemon → Chrome via CDP only** — while implementing in **Go** and using **chromedp** as the CDP client library.

**Scope:** **Google Chrome only**; **no Chrome extension** and **no multi-browser support** — all automation goes through CDP from the daemon. The **daemon never starts the browser**; it only **attaches** to an already-running Chrome with a DevTools debugging endpoint (e.g. `--remote-debugging-port`).

Upstream reference architecture (TypeScript): CLI and MCP talk HTTP to a daemon; the daemon holds CDP connections, dispatches commands, and maintains per-tab state with ring buffers and a global monotonic `seq`.

## Design invariants (ported from bb-browser)

Preserve these invariants:

1. **INV-1:** Operational responses include the **tab id** (the complete CDP target id) and **`seq`**.
2. **INV-2:** Observation-style responses (network / console / errors) include a **cursor** for incremental reads.
3. **INV-3:** Invalid tab id → **hard error** (no silent fallback). A tab id is the **complete CDP target id, verbatim**: exact byte match only — no short alias, prefix/suffix, case-folding or trimming, and never the focused or any other tab in place of an id that was supplied.
4. **INV-4:** **`seq` is globally monotonic** (never decreases).
5. **INV-5:** Events are **isolated per tab** in queries.
6. **INV-6:** Tab close → the id stops resolving (it never comes to mean another target) and that tab’s buffers are **cleared**.
7. **INV-7:** `tab_new` must work when **zero** tabs exist (ordering vs `ensurePageTarget` matters).

## When code exists

- **Build:** `go build -o bb-daemon ./cmd/bb-daemon`
- **Test:** `go test ./...`
- **Daemon:** `bb-daemon` requires `--debugger-url` (or `BB_BROWSER_DEBUGGER_URL`) — e.g. host:port after starting Chrome with remote debugging (`127.0.0.1:9222`). On startup it **attaches via chromedp** (`NewRemoteAllocator` only). Optional **`--tab-idle-timeout`** / **`BB_BROWSER_TAB_IDLE_TIMEOUT`** (default `5m`, `0` disables) closes **daemon-created** tabs after idle; tab-related RPC lines (`action` + JSON-RPC request `body`) append to **`rpc.jsonl`** under **`--state-dir`** / **`BB_BROWSER_STATE_DIR`** (default `~/.local/state/bb-daemon`; `--state-dir -` uses in-memory mode: RPC lines are validated and update managed-tab activity but no history is retained). The global **`seq`** is seeded from the wall-clock nanosecond at startup and incremented in memory (no persisted counter). Persisted managed-tab membership is keyed by **full CDP target id** and changed only by lifecycle records the store writes synchronously (`store.RegisterManagedTab` → `managed_tab_open` on successful `tab_new`, written only after the created target was registered and re-checked afterwards (`commitCreatedTab`), so no open record outlives a removal that raced the creation; `store.RetireManagedTarget` → `managed_tab_retire` on successful `tab_close`, idle close, target-destroyed event, or absence from a **successful** target enumeration). RPC audit lines (asynchronous; `target` is the complete CDP target id the request was resolved to, absent for unresolved requests) never add or remove membership — they only refresh last-activity of the managed target with exactly that id — so a delayed line cannot resurrect a retired tab or touch another tab. Failed closes (other than target-gone) and failed enumerations must not retire. An enumeration may retire only the managed targets that were already persisted **before its CDP request was sent** (`beginManagedReconcile` fixes that candidate set next to `beginTargetEnumeration`; startup and the lifecycle-dirty retry both pass it to `reconcileEnumeratedManaged`): a tab registered by `tab_new` while the request is in flight, or before its reply is reconciled, is never judged absent by that reply. Absence is judged on the reply itself, not on what the registry accepted from it: a candidate the browser listed but the registry refused (removed after the request, or the reply is no longer verifiable) is **not** retired by that reply; it stays persisted and the enumeration is requested again (`MarkTargetDirty`). Idle recovery replays `rpc.jsonl` and restores a tab only when a live target has exactly the persisted full target id. Records without `target` — unresolved requests, and everything written by daemons that logged a short alias under `tab` (a key no longer written or read) — identify no tab and are skipped (one startup warn for such `tab_new` records); never adopt a tab from a short alias or from the `tab` in a request body. A lifecycle write error still updates memory and is logged as warn, never treated as durable. `rpc.jsonl` auto-rotates past **`--rpc-log-max-bytes`** / **`BB_BROWSER_RPC_LOG_MAX_BYTES`** (default 8 MiB) into numbered backups (`rpc.jsonl.1`…, 3 kept); the fresh log is seeded with a snapshot of currently managed tabs (one `managed_tab_open` each, with full target id + last-activity time; retired tabs are not reseeded) so recovery only needs the current file. Replay splits on physical newlines: a corrupt newline-terminated line is warned and skipped (kept on disk, later records still replayed, glued records are not guessed apart); a complete final record missing its newline is replayed and the next write first restores the line boundary; an incomplete final record is truncated. After a failed/short write the next write (append or rotation snapshot) also emits the separator first and refuses to append while that fails. The log keeps request bodies (possibly secrets), so the state dir is created **`0700`** and `rpc.jsonl` plus backups **`0600`** regardless of umask; on startup an existing state dir, active log and `.1`–`.3` backups with wider modes are tightened before replay (stricter modes are never loosened, other files and parent dirs are untouched, a failed chmod fails startup; no-op on Windows). **`POST /v1`** accepts **JSON-RPC 2.0** bodies: **`method`** replaces the old **`action`** field (same string values); arguments live in **`params`**. Methods include **`tab_new`** (optional `url`, optional **`silent`** to open in background without changing focus), **`goto`** (`tab` + `url`), **`tab_close`**, **`tab_select`**, **`tab_list`**, plus **`screenshot`**, **`eval`**, **`click`**, **`fill`**, observation **`network`**, **`console`**, **`errors`** (`tab` + optional **`since`**; **`result`** includes **`events`**, **`cursor`**, optional **`dropped`** — INV-2). Successful **`result`** objects include **`seq`**; **`tab`** when applicable (INV-1).

**Tab identity (breaking change):** short tab ids are gone. `tab` / `focus` / `tabs[].tab` in results and the `tab` param of every targeted method are the complete CDP target id as an opaque string; CLI `--tab` / `--id` pass it verbatim (an explicitly empty `--tab` is an error, not the focused tab). `TabRegistry` keeps no alias layer: `Lookup` is an exact match on registered page targets. A request resolves its tab once (`resolveTab` → `pinTarget`); the per-tab operation lock key, the CDP command, the idle renewal and the audit `target` all use that one id and nothing is re-resolved later — a request that waited for the lock of a tab that vanished meanwhile fails with `unknown tab id`. Only `tab_list` / `tab_focus` (and the CLI when `--tab` is omitted) use the focused tab. Full enumerations are generation-checked in both directions (`TabRegistry.BeginEnumeration` before the CDP request, `ApplyEnumeration` on the reply): a reply never removes a target registered after its request, and never re-registers or lists a target removed after its request (`tab_close`, idle close, destroyed event), so the id of a closed tab cannot resolve again through a late reply. Every removal report counts, also for a target that is already unregistered: the destroyed event after a confirmed `tab_close` refreshes the removal generation, so an enumeration requested between the two cannot bring the id back. Removal generations are kept for the last `maxRemovedTargets` (1024) removed ids only (one slot per id; a repeated report refreshes that slot); a reply older than a forgotten removal registers no unregistered target (a current enumeration or the lifecycle event does). **Applied enumerations are lifecycle points too:** each one confirms the absence of every page target it does not list, registered or not, so a reply registers no unregistered target that an enumeration applied **between its request and its application** did not list (judged on that window, not on which request was sent first — the browser-side order of two overlapping snapshots is unknown; an enumeration that did list the target is not held against it). The last `maxAppliedEnumerations` (64) distinct applied target sets are kept (consecutive identical sets share one entry); a reply older than a forgotten one registers nothing unregistered. **Creation is ordered the same way:** `tab_new` takes the token before `Target.createTarget` and commits the reply with `RegisterCreatedTarget` — a target removed after the token (closed, destroyed, dropped by an enumeration) is not registered, managed, selected or reported as created (`tab closed before tab_new completed`); if that removal may have been forgotten, one current enumeration decides. An enumeration that merely does not list the new target is not a removal (it may predate the creation). Lifecycle *events* still register through `RegisterPageTarget` unconditionally. Do not reintroduce alias generation/parsing, normalization, or fallback; CDP target ids are not promised unique across browser restarts and there is no ownership/lease protocol. Errors use JSON-RPC **`error`** (`code`, `message`, optional **`data`**).

Layout: `cmd/bb-daemon` (daemon); `internal/daemon` (HTTP server, JSON-RPC dispatch); `internal/browser` (remote CDP session); `internal/store` (RPC log + seq); `pkg/protocol` (JSON-RPC + params/result types, importable by dependents); `pkg/daemonclient` (`NewClient` one daemon; `NewPool` many daemons with even spread, per-daemon headers, tab affinity; Pool tab ids are `<backendKey>:<targetId>`); `internal/state` (tab registry, observation buffers).

**Operation budget:** `internal/timeout.Operation` (60s) is the single source for both the daemon's per-RPC CDP deadline and the CLI's whole-command budget (`run` included: tab selection + `eval` share it). Timeout errors name the limit; docs quoting it are checked by `internal/timeout` tests. Do not give the CLI or docs a larger number without raising the daemon limit and `http.Server.WriteTimeout`.

**Optional API token:** daemon merges repeated `--api-token`, comma-separated `BB_BROWSER_API_TOKEN`, and `--api-token-file` / `BB_BROWSER_API_TOKEN_FILE` (flag overrides file environment path; one token per line, blank and `#` comment lines ignored). Trim, deduplicate, ignore empty entries; an empty whitelist disables auth. Unreadable files fail startup without exposing secrets. Configured `POST /v1` (except the explicitly enabled loopback exemption below) requires `Authorization: Bearer <token>`; compare every whitelist entry with `crypto/subtle.ConstantTimeCompare`, without early match returns. Failures return standard HTTP 401 (`unauthorized\n`, plain text, `WWW-Authenticate: Bearer`) before reading the body, RPC dispatch or audit, so no `rpc.jsonl` write. `/live`, `/ready`, `/health` remain public. Never log API tokens. With no tokens, non-loopback listening only emits a startup warn. CLI `--api-token` / `BB_BROWSER_API_TOKEN` sends one token (flag overrides environment); `daemonclient.WithAPIToken` adds the header per client, including independent Pool backend tokens. Whitelist changes require restart; TLS, roles and health auth are out of scope.

**Optional loopback exemption:** `--api-token-allow-loopback` / `BB_BROWSER_API_TOKEN_ALLOW_LOOPBACK` defaults to false (standard `strconv.ParseBool` values; invalid/empty environment values fall back to false; flag overrides environment). With tokens configured, direct TCP loopback `POST /v1` requests without proxy headers bypass Authorization entirely, including wrong tokens. Only `r.RemoteAddr` establishes loopback (`127.0.0.0/8`, `::1`, IPv4-mapped IPv6, with a numeric 0-65535 port; malformed addresses fail closed); never trust `Host` or forwarded addresses. The package-level `proxyHeaders` list contains `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`, `Forwarded`, `CF-Connecting-IP`, `CF-Ray`, `True-Client-IP`, `Via`, `X-Forwarded-Server`, `X-Forwarded-Port`, `X-Forwarded-Scheme`, `X-Original-Forwarded-For`, `Forwarded-For`, `X-Client-IP`, `X-Cluster-Client-IP`; any of these or any `Tailscale-` prefix header disables exemption (case-insensitive presence, even empty values). Normal token authentication then applies. Startup logs one warn with tokens, or an info explaining no effect without tokens; no per-request exemption logs or secrets. Health routes and clients are unchanged. Direct local callers and Tailscale HTTP forwarding (Serve/Funnel default mode, proxy headers preserved) may enable it; forwarded calls still require tokens. Never enable for TCP forwarding (including `tailscale serve --tcp` / `--tls-terminated-tcp`), local reverse proxies that may strip headers, Docker port mappings, cloudflared, or uncertain proxy paths. Header detection is only a fallback, not the primary defense. [Official Serve docs](https://tailscale.com/docs/features/tailscale-serve#identity-headers) document identity headers and their absence for tagged devices/Funnel; [official proxy source](https://github.com/tailscale/tailscale/blob/main/ipn/ipnlocal/serve.go) additionally confirms forwarded headers and `Tailscale-Funnel-Request` (not confirmed in official docs, not live-tested).

**Multi-daemon:** do not put a daemon pool inside callers (e.g. feedscrawler). Use `daemonclient.NewPool(NewClient(urlA, WithHeader(...)), NewClient(urlB, WithHeader(...)))`. Tabs are not shared across daemons. Pool-facing tab ids are `<backendKey>:<targetId>` — the daemon’s complete CDP target id behind the backend key (backendKey defaults to the 0-based constructor index; `NewPoolBackends` can set a name) — matched exactly; a bare target id is rejected rather than guessed onto a backend. `TabNew`, `TabList`, and `TabFocus` return that form; later ops parse the prefix, strip it, and send only the daemon’s own tab id to that backend (no cross-daemon forward/failover). `TabList` queries every backend concurrently, prefixes each id, and merges in constructor order (a down backend is skipped; `*AllFailedError` only if all fail). `TabFocus` also asks all backends concurrently and returns the first healthy one in constructor order (not the fastest), prefixed — not a pool-wide focus. Both wait at most 2s (or the caller's shorter deadline): a backend that has not answered is skipped and its request cancelled, successes already received are returned; with none, the caller's context error (deadline passed) or `*AllFailedError`. Only a success fully decoded inside that budget counts; one completed at or after the deadline is treated as timed out even if it arrives before the call returns. Caller cancellation aborts with `context.Canceled`, discards every answer already received and binds nothing and leaves the caller's result untouched: prefixed results and the whole batch of binding additions and retirements are staged first (the result is decoded into a fresh value outside the lock), and the final cancellation check runs under the pool's tab lock immediately before that batch is committed, so a cancel during fan-out, result preparation or the lock wait still wins; only a cancel after that check is too late. A passed deadline is not a cancellation (in-budget successes are still committed). On success the staged value replaces `*result` as a whole. Each request runs from a snapshot of its backend `Client` (`HTTP`, `BaseURL`, cloned `Headers`, request id from that Client's counter) taken before any request starts, so reconfiguring a `Client` after the call returns is safe. Background requests never change bindings or write the caller's result.

A backend's successful `tab_list` is authoritative for that backend: its bindings no longer in `tabs` are retired (later ops return `*UnknownTabError` locally); failed backends are not reconciled (a reply whose `tabs` is missing, `null` or not an array counts as failed — only an explicit `[]` empties a backend). Only list entries supply binding evidence. A list's `tab` / `focus` fields are metadata. `TabFocus` supplies fresh evidence for the ids it reports and never retires tabs. Ordering uses a pool-local logical clock under a short lock (never across I/O), not daemon `seq`: each `tab_list` / `tab_focus` is evidence of the generation at which it was **sent**; a list retires only bindings whose evidence is older than it, observations older than the newest adopted list are ignored, so a late older list cannot retire newer `tab_new` / observed bindings nor override a newer list, and a newer observation re-binds a live tab an older list retired. `tab_close` / `ForgetTab` take effect when they happen (in-flight older observations cannot revive the id, later ones can); their marks are reclaimed against the earliest in-flight observation (see `pkg/daemonclient/README.md`). Malformed or unknown-prefix ids are rejected. `NewPool` does not health-check at startup. Unbound `tab_new` may fail over to another daemon only to **open a new tab** there.

## Cursor Cloud specific instructions

- **Toolchain:** This module targets **Go 1.26** (`go.mod`). The distro's default `go` is older, so Go 1.26 is installed at `/usr/local/go` and symlinked as `/usr/local/bin/go` (system dep, baked into the VM snapshot). The startup update script only runs `go mod download`. Standard build/test commands are in the README / "When code exists" section above.
- **Running end-to-end requires a real Chrome — the daemon never launches it.** Chrome is preinstalled (`google-chrome`). There is no display, so launch **headless**: `./bb-browser launch --headless --port 9222` (prints `host:port`), then `./bb-daemon --debugger-url 127.0.0.1:9222 --listen 127.0.0.1:8787`. Verify with `./bb-browser health` or `curl 127.0.0.1:8787/health` (`{"status":"ok","browser":"connected"}`; HTTP 503 when CDP is down). The CLI defaults to `http://127.0.0.1:8787`.
- **Gotcha:** `screenshot` on a `data:` URL tab hangs in headless Chrome. Use a real navigable page (`http(s)://` or `file://`) when capturing screenshots.
